# Scenario-driven technology recommendations with OpenLaw Help Clips

Status: MVP specification and single user-facing end-to-end testing seam confirmed. The local tracker records the implementation work. Application implementation is authorized; Ticket 01's required manual asset capture and rehearsal remain incomplete.

## Problem Statement

Lawyers may know the legal task they need to accomplish but lack confidence operating the technologies available to them. Generic tutorials require them to find the relevant instruction and apply it to their situation. Producing short, use-case-specific educational videos manually also takes time.

For the R&T adoption challenge, demonstrate scenario-driven software training through generated audio-video Help Clips that simulate user-system interactions. The supplied screenshots are primarily source material for making those videos. Text provides quick contextual help; a working narrated video is a required core demonstration, not a stretch feature. Prove this within a hackathon without attempting enterprise deployment or substantive legal analysis.

## Solution

Provide a GPT-style Scenario chat where the Learner describes a non-confidential Training objective in free text or selects an optional prepared example. An OpenRouter-routed model interprets the scenario and recommends suitable technologies from a curated tool catalog. Prepared examples make the hackathon demonstration reliable; they are not the only supported input.

The Learner sees suitable technologies, their intended uses, advantages, limitations, and tutorial coverage, then checks one or more recommendations to include in a shared Help Clip. Recommendations must change with the scenario: a comparison objective should prioritize a comparison tool, while a judgment-location objective should prioritize OpenLaw. A combined objective can suggest multiple relevant technologies without inventing operational handoffs between them. Recommendation order is the suggested learning order; it is not a claimed technical handoff.

Below the cards, show one compact shared composer with selected-tool chips, a short coverage statement, screenshot teaching selected for the current objective, an explicit Generate shared Help Clip control, and the generated clip. Do not repeat the full objective or recommendation prose in this section. A continuing contextual conversation is always shown at the bottom after recommendations, including when no checkbox is selected. With checked tools, they provide the question context; without them, the ordered recommendations provide the context. Each question appends a new OpenRouter-generated teaching turn with a direct answer, a visually matched Screenshot Guide when available, coverage, and its own explicit video control. For tools without suitable screenshot evidence or a complete shared plan, explain the coverage limit without inventing a tutorial. A combined video for multiple checked tools still requires scenes for every included tool. The supplied screenshot library currently covers LawNet/OpenLaw and TAFEP; Litera Compare and iManage remain metadata-only.

The target demonstration case is an optional example: "A colleague has given you a judgment name. Use OpenLaw to locate and open the judgment." The complete target has four operations: identify the search field, enter the supplied judgment name, perform the search, and open the matching judgment. The current renderable plan covers only the first operation until the remaining manual assets are captured and rehearsed. A requested Help Clip combines generated supporting narration and audio with reviewed visual states and is labeled "Training demonstration." This case limits tutorial implementation, not the scenarios accepted for recommendations.

The tutor does not observe the other tab, infer successful execution, assess legal relevance, or provide legal advice. If video generation fails, text and screenshot help remain available with a retry option.

## User Stories

1. As a Learner, I want to describe my own non-confidential Training objective in free text, so that recommendations address my task.
2. As a Learner, I want optional sample scenarios such as finding a judgment, comparing documents, or managing a case document, so that I can start quickly without being restricted to one lesson.
3. As a Learner, I want a training-only notice, so that I understand not to enter confidential client or matter information.
4. As a Learner, I want a conversational interface, so that I can describe a difficulty in familiar language.
5. As a Learner, I want follow-up questions to retain the current scenario context, so that I do not have to repeat my objective.
6. As a Learner, I want the configured model to recommend suitable technologies from the catalog for my scenario, so that I can discover tools that address my objective.
7. As a Learner, I want recommendations to reflect the scenario, so that unrelated tools are not presented as necessary to complete my task.
8. As a Learner, I want intended uses, advantages, and limitations for each suggested tool, so that I can understand its role.
9. As a Learner, I want tutorial-coverage indicators, so that I can distinguish available guidance from future coverage.
10. As a Learner, I want to select one or more recommendations for one shared Help Clip, so that I can request one training video for the technologies I chose.
11. As a Learner, I want contextual text about my selected tools, so that I can understand their roles without receiving invented instructions.
12. As a Learner, I want to open the real OpenLaw page alongside the tutor, so that I can perform the software operations myself.
13. As a Learner, I want help locating the search field, so that I know where to begin.
14. As a Learner, I want an instruction for entering the supplied judgment name, so that I can prepare the search.
15. As a Learner, I want a reviewed instruction for running the search, so that I can obtain the corresponding results.
16. As a Learner, I want guidance opening the matching judgment, so that I can finish the training task.
17. As a Learner, I want text guidance first, so that I can obtain help without waiting for video generation.
18. As a Learner, I want the Help Clip to show the actual reviewed interface screenshots with animated guidance, so that I can see how the operation is performed.
19. As a Learner, I want to ask about any supported step, so that Help Focus follows my current question without requiring completion controls.
20. As a Learner, I want to request a shared Help Clip explicitly, so that video generation happens only when I choose it.
21. As a Learner, I want the Help Clip to focus on my difficulty, so that its explanation is useful to my current Help Focus.
22. As a Learner, I want narration and captions built around reviewed core instructions, so that personalization preserves the operational steps.
23. As a Learner, I want highlights, cursor motion, and a reviewed next state, so that the video demonstrates the interaction visually.
24. As a Learner, I want clips labeled as training demonstrations, so that I do not mistake them for recordings of my own work.
25. As a Learner, I want a clear coverage-limit response for unsupported actions or tools, so that I am not shown a fabricated tutorial.
26. As a Learner, I want grouped text help to remain when a clip fails, so that I can continue learning.
27. As a Learner, I want a simple video retry option, so that I can request another attempt.
28. As a Learner, I want legal interpretation left to me, so that the tutor's software-training role is clear.
29. As a Learner, I want a document-comparison scenario to produce different recommendations from a judgment-search scenario, so that the assistant responds to my task rather than replaying a fixed demo.
30. As a Learner, I want relevant tools suggested for a combined task, so that I can understand their separate roles without being promised an unverified cross-tool workflow.
31. As a Learner, I want an unavailable selected combination to explain what is missing, so that the tutor does not create a partial or fabricated combined video.
32. As a Learner, I want one current OpenLaw-only selection to generate a narrated MP4, so that the prototype proves the audio-video path.
33. As a Learner, I want to ask a follow-up without first selecting a video tool, so that questions are not blocked by the optional Help Clip selection.
34. As a Learner, I want the tutor to answer my current wording and choose only a supplied screenshot that materially supports it, so that a sorting question is not answered by a fixed date-filter rule.

## Implementation Decisions

- **Application shape:** one tutor application, a small curated tool catalog, one reviewed OpenLaw workflow, and local training assets. No application code or existing module interfaces are present in the repository. Do not add distributed services or general workflow-planning machinery.
- **Scenario entry and recommendations:** accept free-text non-confidential scenarios from the start, with optional sample shortcuts. An OpenRouter-routed model interprets the objective and selects relevant technologies from the curated catalog. Aim for roughly three suggestions when relevant; do not pad a simple task with unrelated recommendations or always return the same list. Dynamic recommendations are a working MVP capability, not a static preview of future behavior.
- **Catalog:** maintain tool names, capabilities, intended uses, pros, cons, and tutorial-coverage status. OpenLaw and TAFEP have supplied screenshot libraries; only the original OpenLaw Search-field action is a manually reviewed action. Litera Compare and iManage need only curated metadata for recommendation and high-level text help. Do not claim unverified capabilities or endorsement.
- **Selection and text help:** each recommendation card has an accessible checkbox labelled "Include in shared Help Clip". Selecting cards is solely video input; it does not open an individual application-help panel. Adapt grouped high-level explanations to the scenario even without visual coverage, clearly stating what assets or Lesson Plan are missing. Give precise operational instructions only where reviewed guidance supports them.
- **Lesson Plans and coverage:** a Lesson Plan is the server-side, manually curated mapping from one exact selected tool set to an ordered list of reviewed scenes. It contains every screenshot, highlight, cursor target, expected state, and fixed core instruction needed to render. Eligibility depends on resolving that exact plan, not merely the presence of a tool or one covered action. Current coverage is the single OpenLaw Search-field plan. A multi-tool set is unavailable until reviewed scenes for every selected tool and an explicit multi-tool Lesson Plan are added.
- **Scenario context:** retain the Learner's entered or selected Training objective, relevant conversation, recommendations, selected tool IDs, and Help Focus for the active Scenario chat. Help Focus identifies the question currently being discussed; it does not record completed work. A newly submitted scenario clears the selection, question, guidance, and generated clip. Enterprise matter isolation is not a claim of this prototype.
- **Contextual teaching turns:** Ask calls a dedicated contextual-question endpoint rather than the selection-coverage endpoint. The composer is available after recommendations even with no checked tools. Checked IDs narrow the context; otherwise the current ordered recommendations are sent. Each result appends the learner question, an OpenRouter-generated direct answer, grounding status, relevant Screenshot Guides, coverage, and optional question-bound Help Clip to the conversation. Generating media in one turn does not replace another turn's media.
- **Context window:** keep the latest three complete contextual question-and-answer turns by default, configured through `NEXT_PUBLIC_CONTEXTUAL_QUESTION_WINDOW`. Enforce the bound in both the client request and server before calling OpenRouter. Older turns remain visible but are not sent as memory.
- **Screenshot index and selection:** asset preparation scans every PNG in the LawNet, TAFEP, and Judiciary.gov.sg screenshot directories and validates it against the human-reviewed Markdown files under `docs/references/`. The build fails for missing, duplicate, or unknown filename references. It writes `public/assets/screenshots/manifest.json`, `image-keywords.json`, and `reference-metadata.json` with filename-derived terms plus the reviewed website/product identity, visible controls, filters, and captured state. For each question, OpenRouter searches the reference-enriched index belonging to the checked or recommended tools using the scenario, current question, and recent conversation. It then receives the same reviewed metadata beside each shortlisted image, visually inspects the candidates, chooses at most one exact image ID, writes the direct answer, and locates the relevant region in a second vision pass. The server resolves the ID to the fixed full-resolution asset and signs the resulting scene. No question-specific keyword-to-answer or keyword-to-screenshot mapping exists in application code.
- **Workflow:** the target OpenLaw tutorial path is a manually reviewed, end-to-end rehearsed sequence for locating and opening a judgment by its supplied name. It remains incomplete until Ticket 01's evidence is captured and rehearsed. Free-text scenarios may receive recommendations without matching this path. AI may dynamically recommend tools and explain their roles, but operational tutorials remain manually verified: no invented operations, reordered dependencies, or untested cross-tool handoffs.
- **Action content:** each Verified Action contains a known starting condition, a manually written reviewed core instruction, its expected result, and relevant visual assets. Keep instructions as simple curated data; no general authoring or verification platform is required.
- **Visual evidence:** screenshots belong to specific interface states. Highlights and simulated pointer positions must match the associated image, including its layout. Do not reuse positions from an expanded sidebar on a collapsed-sidebar capture. Show the actual captured expected next state rather than fabricating a replacement interface.
- **Purpose of screenshots:** use them primarily as video scene assets. Remotion adds cursor movement, highlights, zoom, captions, and transitions between reviewed states; OpenRouter selects a bounded supporting emphasis and produces the narration audio through TTS. Standalone screenshot assistance is supplementary. A chat response containing an image does not satisfy the audio-video deliverable.
- **Text and narration:** preserve essential operational instructions and reviewed scene captions. The model may select only a curated supporting narration emphasis; the app combines that selection with reviewed copy before synthesis. This keeps personalization within verified coverage without a complex semantic-validation system.
- **Help Clip generation:** only an explicit Generate Help Clip request or explicit retry starts generation. AI can select eligible screenshot support without starting video. For a single checked tool or contextual answer, the server stores the AI-selected screenshot ID, instruction, caption, and highlight in a signed, expiring token and re-resolves the original asset before rendering. A multiple-tool shared clip still requires scenes for every checked tool. OpenRouter TTS produces audio, and Remotion with FFmpeg renders the supplied screenshot, highlight, caption, and evidence status into one MP4. Audio duration informs scene timing.
- **Personalization:** adapt grouped explanation and instructional emphasis to the Help Focus, while preserving the Lesson Plan's reviewed scene order and core instructions. The model may describe selected tools' curated roles; it must not invent interfaces, steps, or cross-tool handoffs.
- **External exercise:** the Learner operates the real OpenLaw page in a separate browser tab. The tutor does not inspect, control, or monitor that tab.
- **Help Focus:** follow the Learner's current question or supported step. Do not build progress tracking, completion controls, completion labels, or associated completion state.
- **Unsupported guidance:** explain the coverage limit for an uncovered tool, action, or combination. Do not generate a new clip from unverified UI instructions.
- **Failures:** retain the reviewed text and annotated screenshot, display a simple inability-to-generate message, and provide Retry Video. No durable job queues, automatic recovery system, or production availability target is required.
- **Input boundary:** accept free-text generic or synthetic Training objectives and follow-ups; offer prepared examples as optional shortcuts. No real document uploads. Display "Training environment — do not enter confidential client or matter information." Free-text input does not authorize confidential matter handling, and the notice is not a claim of automated confidential-data detection.
- **Technology decisions:** OpenRouter supporting generation and TTS, Remotion, and FFmpeg are selected. The OpenAI TypeScript SDK is used only as OpenRouter's compatible client. Frontend framework, database, hosting, SDK version, model choice, and exact endpoint shapes have not been selected; resolve those as simple implementation choices when coding is authorized rather than presenting the original concept's stack as binding.

## Testing Decisions

The single user-facing end-to-end testing seam is confirmed. Keep checks lightweight for the hackathon: controlled AI/media responses for repeatable user-visible behavior, plus one real generated narrated-video check.

- **One primary seam:** exercise the complete tutor application through the same user-facing interactions the Learner uses. Test the observable scenario-to-guidance-to-Help-Clip flow, not internal helper functions or the arrangement of modules.
- **Repeatable checks:** substitute controlled generation/media outcomes at the external dependency boundary so application behavior can be checked without repeatedly paying for narration and rendering. This is a testing convenience, not a new product subsystem or substitute for the real demo.
- **Scenario-driven recommendations:** enter a free-text comparison objective and a free-text judgment-location objective. Check that the recommendations and explanations reflect their different capabilities, rather than returning a fixed OpenLaw-first lesson. For a combined objective, check that suggested tools' roles are explained without inventing a cross-tool operational sequence. Test relevance and catalog membership, not exact AI wording or a mandatory count of three.
- **Optional samples:** the OpenLaw sample starts the reliable demonstration, while the free-text entry remains available without selecting a sample. Entering a comparison objective must not start the OpenLaw workflow.
- **Selection UI:** a multi-tool scenario shows multiple checkboxes and no Explore buttons. Selecting and deselecting cards updates the selected summary in recommendation order; submitting a new scenario clears it.
- **Covered path:** select OpenLaw alone for a matching objective, request contextual help, and explicitly request the supported shared Help Clip. Check that the demonstration is shown in the right scenario and Help Focus.
- **Uncovered path:** select a relevant tool without tutorial assets, or a multi-tool set with no matching Lesson Plan. Check that grouped contextual text and the coverage label remain available, generation is disabled, and the task is not redirected into an unrelated lesson. A forged generation request for this selection must be rejected by the server.
- **Explicit request:** asking an ordinary question or receiving a screenshot must not start video generation. A Help Clip request and retry are explicit interactions.
- **Continuing questions:** the composer remains visible with no checked tools. A question about LawNet Legal Resources searches all 27 indexed LawNet images and may select the supplied Legal Resources menu or LawNet research screen after visual inspection; it cannot fall back to the fixed Search-field screenshot. A later reference such as "where is the first option?" uses the recent conversation when searching and answering. Earlier turns remain visible.
- **Core audio-video acceptance:** the prototype is incomplete without a working on-demand narrated MP4 that simulates a supported interaction using the screenshots. The Learner can request it from contextual guidance without first viewing a standalone screenshot. Text and still-image output alone do not pass this check.
- **Coverage:** an uncovered tool, action, or selected combination receives an explanatory response and cannot start visual tutorial generation. An OpenLaw entry alone does not bypass missing action assets or create a multi-tool plan.
- **Failure:** a failed clip leaves useful grouped text help and a working retry interaction.
- **Manual real-media check:** generate at least one real Help Clip using the OpenRouter supporting-style selection/TTS path and the chosen renderer. Inspect playback, audible narration, legible captions, aligned highlights, and the reviewed next state. Confirm the essential operational instruction was preserved. Once a multi-tool Lesson Plan exists, inspect one real MP4 with scenes for every selected tool. Do not test incidental style choice or pixel positions as acceptance criteria.
- **Manual workflow rehearsal:** carry out the four operations on the real OpenLaw page using the chosen judgment and confirm the matching judgment opens. This is manual preparation and demo verification, not runtime automation or automatic completion detection.
- **Prior art:** the repository currently contains a README, design documentation, and screenshots; there is no application test suite or existing testing seam to reuse. Do not introduce multiple layers of tests merely to create coverage.

## Out of Scope

- Legal advice, legal relevance assessment, enforceability analysis, or other autonomous legal conclusions.
- Arbitrary AI-generated operational workflows or cross-tool execution and handoffs. Dynamic scenario interpretation and tool recommendations are explicitly in scope.
- Tutorial implementation or complete screenshot libraries for tools other than a reviewed Lesson Plan.
- Full-workflow video generation, general video editing, or generative imitation of an interface.
- Browser/computer-use agents, runtime live inspection, control of the Learner's tab, or automatic UI-change detection.
- Progress tracking, completion controls and labels, automatic completion detection, or claims that a watched clip proves successful execution.
- Confidential matter/document handling, real client uploads, enterprise authentication, or production privacy infrastructure.
- Production-grade reliability, complex narration validation, distributed processing, automatic failure recovery, and broad tutorial coverage.
- Proving sustained adoption through analytics or longitudinal evaluation during this prototype.
